## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | 크로우의 만물상 (Crow's Curiosity Shop) |
| 형태 | 단일 HTML 파일 웹 챗봇 (HTML + CSS + Vanilla JS) |
| 방식 | **규칙 기반(Rule-based)** — 키워드 매칭, 외부 API 미사용 |
| 목표 | 페르소나가 일관된 캐릭터와 대화하는 몰입형 챗봇 제작 |

### 개발 4대 규칙 (기획 단계에서 확정)

1. **페르소나 일관성 유지** — 캐릭터가 갑자기 다른 사람처럼 말하면 몰입이 깨진다.
2. **규칙 기반 설계** — 모든 대화를 이해할 수 없으므로 핵심 키워드에 반응하도록 설계한다.
3. **캐릭터다운 회피** — 모르는 질문에 "모른다"고 딱딱하게 답하지 않고, 캐릭터답게 자연스럽게 둘러댄다.
4. **대화 흐름 사전 설계** — 인사 → 키워드 응답 → 마무리/초기화 흐름을 미리 정한다.

## 2. 캐릭터 기획 (1단계: 기본 설정 8문항)

| 문항 | 설정 |
|---|---|
| 이름 | 크로우 (Crow) |
| 정체 | 기억과 행운을 거래하는 영리한 까마귀 |
| 특징 한 줄 | 반짝이는 물건을 좋아해서 사용자가 좋은 아이디어를 낼 때마다 눈독을 들임 |
| 성격 키워드 3개 | 영악함, 신비로움, 위트 |
| 말버릇 | "~까악", "~라구" |
| 대표 이모지 | 🦅, 💎 |
| 사용자 호칭 | "단골손님", "반짝이" |
| 한 문장 소개 | 인생이라는 모험에서 당신이 길을 잃지 않도록 묘한 힌트와 행운을 툭 던져주는 영리한 조력자 |

**페르소나 일관성 장치**: 모든 대사에 ① 말버릇("까악", "~라구") ② 상인 세계관 어휘(거래, 장부, 보물, 손님) ③ 이모지 포인트를 반드시 포함시켜, 어떤 응답이 나와도 "같은 캐릭터"로 느껴지게 했다.

## 3. 키워드 응답 설계 (2단계: 총 12개 규칙)

> 표의 한 줄 = 코드의 `{ keywords: [...], reply: '...' }` 한 줄

### 필수 카테고리 8개

| # | 카테고리 | 반응 키워드 | 응답 요지 |
|---|---|---|---|
| 1 | 인사 | 안녕, hi, 하이, 반가워, hello | 단골손님 환영 + 상점 소개 |
| 2 | 이름 소개 | 이름, 누구, 네이름 | "위대한 까마귀 상인 크로우" 자기소개 |
| 3 | 특기/전문분야 | 특기, 잘해, 전문, 능력 | 행운 찾기 + 나쁜 기억 먹어치우기 |
| 4 | 고민 상담 | 고민, 힘들, 속상, 우울 | 고민을 "거래 가치"로 받아주며 위로 |
| 5 | 칭찬받았을 때 | 잘한다, 멋져, 최고, 천재 | 우쭐대며 행운의 깃털 선물 |
| 6 | 놀림/무례한 말 | 바보, 못생, 멍청 | 블랙리스트 경고 (화내되 캐릭터답게) |
| 7 | 심심할 때 | 심심, 놀아줘, 놀자 | 재밌는 기억을 팔라고 거래 제안 |
| 8 | 작별 인사 | 잘가, bye, 바이, 갈게 | 다음 방문 기약 인사 |

### 자유 카테고리 4개 (세계관 확장)

| # | 카테고리 | 반응 키워드 | 응답 요지 |
|---|---|---|---|
| 9 | 좋아하는 것 | 좋아하는, 보물, 반짝이, 취미 | 빛나는 것에 사족을 못 씀 |
| 10 | 나이 | 나이, 몇 살, 언제 태어 | 신비로운 장수 설정 |
| 11 | 두려운 것/약점 | 무서운, 약점, 싫어하는 | 허수아비를 무서워하지만 부정함(츤데레) |
| 12 | 행운 거래 | 행운, 뽑기, 운세, 타로 | **타로 API 연동** — 거래 성립 대사 후 실제 카드를 뽑아 운세 풀이 (→ 11장 참고) |

### 예외 상황 3가지 (3단계)

| 상황 | 처리 |
|---|---|
| 첫 인사말 (GREETING) | 챗봇 열면 자동 출력 — 상점 입장 환영 대사 |
| 모르는 질문 (FALLBACK_REPLIES) | 2종 준비, **랜덤 선택** — "보물창고에 없는 희귀한 단어", "행운의 장부에 없다" 등 캐릭터답게 회피 |
| 초기화 버튼 (RESET_MESSAGE) | 첫 인사와 **다른 전용 대사** — "거래 장부를 새로 고쳤다"로 리셋을 세계관 안에서 표현 |

## 4. 대화 흐름 설계

```
[페이지 접속]
     │
     ▼
 GREETING 자동 출력 (크로우가 먼저 말을 건다)
     │
     ▼
 사용자 입력 ──→ 키워드 매칭 검사 (RESPONSES 배열 순서대로)
     │                │
     │           ┌────┴────┐
     │        매칭 성공   매칭 실패
     │           │         │
     │      해당 카테고리  FALLBACK_REPLIES
     │        응답 출력    중 랜덤 출력
     │           └────┬────┘
     │                ▼
     └──────── 대화 반복 (인사 → 키워드 응답 → 작별)
                      │
                      ▼
          [🔄 새 거래 버튼] → 대화 전체 삭제 + RESET_MESSAGE 출력
```

## 5. 화면(UI) 설계

**컨셉**: "밤하늘 아래 까마귀의 골동품 상점" — 검보라 배경 + 금빛(반짝이) 포인트 컬러로 캐릭터 세계관을 시각화.

| 영역 | 구성 요소 | 기획 의도 |
|---|---|---|
| 헤더 | 아바타(🦅) + 이름/한 줄 소개 + 🔄 새 거래 버튼 | 누구와 대화하는지 항상 표시, 초기화도 "새 거래"로 세계관 용어 사용 |
| 대화 영역 | 말풍선 (크로우: 보라 / 사용자: 금색) | 발화자 구분을 색으로 직관화, 등장 애니메이션으로 생동감 |
| 추천 키워드 칩 | "안녕", "오늘 운세 봐줘" 등 6개 버튼 | 규칙 기반 챗봇의 최대 약점(뭘 물어봐야 할지 모름)을 보완 |
| 입력 영역 | 텍스트 입력 + 보내기 버튼 (Enter 지원) | 기본 채팅 UX |
| 타이핑 표시 | ··· 점 애니메이션 후 0.5~0.9초 뒤 응답 | 즉답보다 "생각하고 답하는" 느낌으로 몰입도 상승 |

## 6. 개발 과정 (구현 순서)

### STEP 1 — 데이터 구조 정의
설계표의 내용을 코드로 1:1 변환. 표의 한 줄이 배열의 한 원소가 되도록 구조화했다.

```js
const GREETING = '까악! 반짝이는 영혼을 가진 손님이 찾아왔군. …';
const RESET_MESSAGE = '까악! 거래 장부를 싹 새로 고쳤군! …';
const FALLBACK_REPLIES = [ '까악? 방금 그 말은 내 보물창고에도 없는…', '…' ];
const RESPONSES = [
  { category: '인사', keywords: ['안녕', 'hi', '하이', …], reply: '까악! 새로운 단골손님이…' },
  // … 총 12개 규칙
];
```

### STEP 2 — 키워드 매칭 로직

```js
function findReply(input) {
  const text = input.toLowerCase();            // 대소문자 통일 (bye, BYE 모두 대응)
  const textNoSpace = text.replace(/\s+/g, ''); // 공백 제거 ("몇 살" = "몇살")

  for (const rule of RESPONSES) {
    for (const kw of rule.keywords) {
      if (text.includes(kw) || textNoSpace.includes(kw.replace(/\s+/g, ''))) {
        return rule.reply;                     // 먼저 걸리는 규칙 우선
      }
    }
  }
  return FALLBACK_REPLIES[Math.floor(Math.random() * FALLBACK_REPLIES.length)];
}
```

**설계 판단**:
- `includes()` 부분 일치 방식 → "안녕하세요", "너 이름이 뭐야?" 같은 문장 속 키워드도 잡아낸다.
- 배열 순서 = 우선순위 → 위에서부터 검사하고 먼저 걸리면 즉시 반환.
- 키워드를 어간 위주로 등록("힘들어" 대신 "힘들") → "힘들다", "힘들어요" 등 어미 변화에 모두 대응.

### STEP 3 — 채팅 UI 구현
- `addBubble(text, who)` 함수 하나로 봇/사용자 말풍선을 모두 생성 (who 값으로 스타일 분기).
- 메시지 추가 시 `scrollTop = scrollHeight`로 자동 스크롤.

### STEP 4 — 몰입 요소 추가
- **타이핑 인디케이터**: ··· 애니메이션을 먼저 띄우고 500~900ms 랜덤 지연 후 답변으로 교체.
- **추천 키워드 칩**: 클릭하면 해당 문장이 자동 입력·전송.
- **초기화**: 대화 내역 삭제 후 RESET_MESSAGE 출력 (GREETING과 다른 대사).

### STEP 5 — 예외 처리
- 빈 입력(공백만) 전송 방지: `trim()` 후 빈 문자열이면 무시.
- XSS 방지: 사용자 입력을 `innerHTML`이 아닌 `textContent`로 삽입.

## 9. 회고 및 확장 아이디어

### 규칙 기반 방식의 한계와 보완
- **한계**: 등록된 키워드 밖의 질문은 이해하지 못한다. 유의어("굿바이" 등)를 일일이 등록해야 한다.
- **보완한 것**: 추천 키워드 칩으로 "물어볼 수 있는 것"을 노출, 어간 매칭 + 공백 제거로 변형 입력 대응, 캐릭터다운 FALLBACK으로 실패 순간에도 몰입 유지.

### 확장 아이디어
1. 카테고리별 응답을 배열로 만들어 **같은 질문에도 매번 다른 대답** 출력 (반복 대화 시 몰입 유지)
2. `localStorage`로 대화 기록 저장 → 재방문 시 "또 왔군, 단골손님!" 분기
3. 행운 거래 키워드에 실제 **랜덤 운세 뽑기 기능** 연결 (미니 콘텐츠화)
4. 감정 상태 변수 추가 — 무례한 말이 누적되면 응답 톤이 점점 차가워지는 시스템
5. LLM API 연동 버전으로 업그레이드하고, 규칙 기반 버전과 응답 품질 비교 (QA 포트폴리오 소재)

## 11. 기능 확장 — 타로 운세 API 연동 (tarotapi.dev)

규칙 기반 챗봇에 처음으로 **외부 API**를 연동한 기능. "운세/타로/뽑기/행운" 키워드가 걸리면 크로우가 실제 타로 카드 한 장을 뽑아 운세를 풀이해준다.

### 사용 API

| 항목 | 내용 |
|---|---|
| 엔드포인트 | `GET https://tarotapi.dev/api/v1/cards/random?n=1` |
| 인증 | 불필요 (무료 공개 API) |
| CORS | `access-control-allow-origin: *` → 로컬 HTML 파일(file://)에서도 직접 호출 가능 (사전 검증 완료) |
| 응답 필드 | `type`(major/minor), `name`, `name_short`(ar00~ar21), `suit`, `value`, `meaning_up`, `meaning_rev` |

### 연출 흐름

```
"운세 봐줘" 입력
   │
   ▼
① 거래 성립 대사 ("대가는 비밀 하나로 받아두지…") — 페르소나 유지
   │
   ▼
② 카드 뽑는 중… (타이핑 애니메이션, 최소 1.2초 유지해 기대감 연출)
   │  └─ 이 사이에 fetch()로 API 호출
   ▼
③ 결과 출력 — 금테 카드 말풍선 (🎴 카드명 — 정/역방향 + 크로우 풀이 + 옛 장부 원문)
   │
   └─ API 실패 시: "수정구에 안개가 자욱해…" (캐릭터답게 회피, 규칙 ③ 적용)
```

### 설계 판단 (한글화 처리)

API가 **영어 데이터만 제공**하므로, 그대로 노출하면 페르소나 몰입(규칙 ①)이 깨진다. 이를 위해 3단 변환 구조를 설계:

1. **카드명 한글화** — 메이저 아르카나 22장은 `name_short → 한글명` 매핑 테이블(`MAJOR_KO`), 마이너 56장은 `슈트(완드/컵/소드/펜타클) + 랭크(2~10/에이스/페이지/나이트/퀸/킹)` 조합으로 자동 생성 → 78장 전체 커버.
2. **크로우식 풀이** — 메이저 22장은 카드별 정/역방향 해석 44종(`MAJOR_FORTUNE`), 마이너는 슈트별 정/역방향 해석 8종(`SUIT_FORTUNE`)을 크로우 말투로 작성.
3. **원문 인용** — API의 영어 의미(`meaning_up/rev`) 첫 문장을 *"서쪽 대륙의 옛 장부 원문"*으로 첨부 → API 데이터를 실제로 사용하고 있음을 보여주면서 세계관 안에서 소화.

정방향/역방향은 API가 주지 않으므로 클라이언트에서 뽑을 때 50% 확률로 결정한다.

### 카드 이미지 표시

tarotapi.dev는 텍스트만 제공하고 이미지가 없다. 대신 이 API의 기준 덱인 **라이더-웨이트(Rider-Waite) 원본 그림이 퍼블릭 도메인**이라 sacred-texts.com에 78장 전체가 공개되어 있고, **파일명이 API의 `name_short`와 정확히 일치**한다는 점을 활용했다.

| 항목 | 내용 |
|---|---|
| 이미지 URL 규칙 | `https://www.sacred-texts.com/tarot/pkt/img/{name_short}.jpg` (예: ar01 → 마법사) |
| 사전 검증 | 78장 전체 URL을 스크립트로 일괄 확인 → **전부 200 OK** |
| 역방향 연출 | CSS `transform: rotate(180deg)`로 카드를 실제로 뒤집어 표시 |
| 로드 후 처리 | 이미지 로드 완료 시 채팅 스크롤 재조정 (그림 높이만큼 밀리는 문제 방지) |
| 실패 대비 | `onerror` 시 이미지만 제거하고 텍스트 운세는 유지 (호스트 측 봇 차단이 간헐적으로 관측되어 방어 코드 필수) |

> **QA 메모**: Node.js 테스트에서는 같은 이미지 URL이 간헐적으로 403(봇 차단)을 반환했지만, 브라우저 UA로는 일관되게 200이 확인됨. 실제 사용 환경(브라우저)에서는 정상 로드되며, 만일을 대비해 이미지 실패 시 텍스트만 남기는 우아한 성능 저하(graceful degradation)를 적용.

### 오늘의 행운 추천 (마무리 문장)

타로 풀이의 마지막 문장으로, 크로우의 관점에서 **행운의 물건·색깔 / 피해야 할 물건·색깔을 각 1개씩** 랜덤 추천한다.

| 풀 | 개수 | 콘셉트 |
|---|---|---|
| 행운의 물건 | 15종 | 반짝이는 것을 좋아하는 까마귀 취향 (반짝이는 동전, 호일 껍질, 은색 볼펜, 유리구슬…) |
| 행운의 색깔 | 9종 | 빛나는 색 (금색, 은색, 별빛 노랑, 까마귀 깃털의 검보라…) |
| 피할 물건 | 10종 | 광택 없는 것 + 크로우의 천적 (허수아비 인형, 눅눅한 종이상자, 녹슨 못…) |
| 피할 색깔 | 7종 | 탁한 색 (잿빛, 흙탕물 갈색, 지푸라기색…) |

출력 형식 (점선 구분선 아래 금색 텍스트):

```
🍀 행운의 물건: 반짝이는 동전 · 행운의 색깔: 금색
🚫 피할 물건: 짝 잃은 양말 · 피할 색깔: 잿빛
내 보물창고 감정 기준이니 틀림없다구, 까악!
```

물건/색깔 풀 자체를 "까마귀가 좋아할 것(반짝임) vs 싫어할 것(광택 없음, 허수아비)"으로 설계해, 랜덤 뽑기 결과도 항상 페르소나(규칙 ①)를 벗어나지 않는다.

### 2턴 대화(상태 관리) 설계

단순 키워드 반응을 넘어, 크로우가 **먼저 묻고 답을 기다리는** 흐름을 도입했다 (`pendingWorry`, `pendingWeather` 상태 변수).

```
[고민 상담]                          [날씨 — 지역 미지정]
"고민 있어"                          "날씨 알려줘"
  → 크로우: "어떤 고민인지 털어놔 보라구!"   → 크로우: "어느 동네 하늘을 정찰해줄까?"
"면접 망한 것 같아..."                "부천"
  → 크로우: "그 꿀꿀한 기억은 내가 홀라당     → 정찰 연출 후 부천 실시간 날씨 보고
     쪼아 먹어 버렸으니 걱정 말라구! …"
```

- 대기 상태에서 **다른 주제의 키워드가 들어오면** 그 규칙을 우선 처리하고 대기 상태를 해제 (대화가 자연스럽게 전환)
- 초기화(새 거래) 버튼도 대기 상태를 함께 리셋

### 날씨 기능 상세 (Open-Meteo 연동)

```
"부천 날씨 어때?" / "날씨 알려줘 부천" 입력
   │
   ▼ parseCity() — ① 등록 지역 키워드(24곳)가 문장 어디에 있든 인식
   │               ② 미등록 지역은 "지역명+날씨/기온" 패턴 추출 (오늘/지금 등 비지역어 제외)
   │               ③ 지역이 없으면 → "어느 동네 하늘을 정찰해줄까?" 되묻고 다음 입력을 지역명으로 받음
   ▼ geocodeCity() — 지역명 → 위도/경도
   │   1단계: 주요 도시 24곳 내장 좌표 테이블에서 즉시 조회 (API 불필요)
   │   2단계: 없으면 지오코딩 API — 접미사 변형(시/광역시/특별시) 순차 조회,
   │           인구 5만↑ 결과 조기 채택, 전부 실패 시 1회 재시도
   ▼ Forecast API — current=temperature_2m,weather_code
   ▼ WMO 날씨 코드(10개 그룹) → 한국어 설명 + 크로우의 한마디
   ▼ "까악! 정찰 보고 도착! 지금 부천 하늘은 '대체로 맑음', 기온은 25도라구! 🌡️ …"
```

**설계 판단 (QA 기록)**:
- **지오코딩 API의 한계 발견**: 한글 축약 지명("부천", "서울")은 엉뚱한 마을을 반환하거나 결과가 없고, 정식 행정명("부천시", "서울특별시")만 정확히 검색됨 → 접미사 변형 순차 조회 + 인구 기준 선별로 해결.
- **속도 제한(rate limit) 대응**: 테스트 중 연속 요청 시 간헐적 빈 응답 확인 → 주요 도시 24곳은 내장 좌표 테이블로 API 호출 자체를 제거하고, 미등록 지역만 API 경로 사용 (재시도 1회 포함).
- **밸런스 게임 우선순위**: "짜장 아니면 짬뽕 뭐 먹지?"는 메뉴 키워드('뭐 먹')와 밸런스 키워드('아니면')가 동시에 걸림 → RESPONSES 배열에서 밸런스 규칙을 메뉴보다 앞에 배치해 양자택일을 우선 처리.
- **응답 배열화**: `reply`가 배열이면 랜덤 선택하도록 공통 로직 확장 — 감정 쓰레기통(3종)에 우선 적용, 다른 카테고리도 배열로 바꾸기만 하면 됨.

추천 키워드 칩도 새 기능이 보이도록 교체: `안녕 · 운세 봐줘 · 날씨 알려줘 · 메뉴 추천 · 심심해 · 고민 있어`
