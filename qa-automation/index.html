무엇을 만들었나

기획서나 기존 TC를 넣으면 TC 작성 → 규칙 점검 → 게임 자동 테스트 → 결과 리포트·TC 엑셀 → Jira 이슈 등록까지 이어지는 흐름입니다. 중심에는 제가 정리한 TC 작성 규칙이 있고, AI가 TC를 쓸 때와 점검 도구가 TC를 볼 때 모두 이 규칙을 따릅니다.

기획서 PDF·이미지·기존 TC 엑셀→ TC 작성 (Claude Code + TC 작성 규칙)→ 규칙 점검→ Playwright 자동 테스트→ 리포트·TC 엑셀→ Jira TC·버그 이슈

게임 파일이 없으면 자동 테스트는 건너뛰고, 기존 TC 검토 의견·기획서 확인 필요 사항·추가 제안을 정리하고 끝납니다.

TC 작성 규칙 (공개 자료 + 제가 쓴 TC 2종을 참고해 정리)

  • 한 줄 쓰기 — TC 하나에 확인 하나, 기대 결과는 눈으로 확인할 수 있는 결과(숫자·화면 문구 그대로)
  • 무엇을 TC로 — 정상·실패 짝, 경계값(n−1·n·n+1), 끊김·환경, 확률은 시행 횟수와 판정 범위
  • 빠짐없이(커버리지) — 화면 요소·안내 문구·규칙 값마다 TC, 근거(기획서 조항·화면)마다 TC가 0건인 칸이 없게

직접 써 보기 (설치 없음)

TC 엑셀이나 기획서 PDF를 넣으면 위 규칙으로 점검하고, 기획서에는 있는데 TC에 없는 문구·버튼·수치를 찾아 줍니다. 파일은 브라우저 안에서만 읽고 어디에도 올라가지 않습니다.

AI가 쓴 TC는 모두 초안이며 제가 검토 중입니다(엑셀의 검토 칸). Jira에는 기존 TC·결함을 등록했고, 이번에 보충한 TC는 아직 올리지 않았습니다.

어떻게 테스트했나

  • 내부 값을 읽을 수 있는 게임(BLOODFALL·카드팩): 게임 상태를 직접 맞춰 원하는 상황을 빠르게 만들고(보스 등장 직전, 체력 30% 등) 화면과 값을 함께 판정
  • 내부 값이 숨겨진 게임(슬라임): 페이지가 열리기 전에 물리 엔진 생성 함수를 감싸, 원하는 단계 슬라임을 원하는 자리에 놓아 병합 점수·경고선 경계(59/60/61%)를 확인
  • 온라인 기능: 실제 P2P 대신 가짜 연결로 연결 문구·시간 초과(시계를 빠르게 돌림)·승패 메시지를 확인, 실제 두 기기 연결은 수동 TC로 남김
  • 무작위: 난수를 고정하거나, 확률은 수천~수만 번 뽑아 범위로 판정 (예: 아이템 박스 2,000마리 중 70~130개)

AI와 제 역할 나누기

제가 정한 것무료 도구만 쓰기, TC 작성 규칙, 테스트할 게임과 기획서, AI 결과 검토·채택
AI(Claude Code)가 한 것규칙대로 TC 초안 작성, 테스트 코드·도구 코드 작성, 실행 결과 정리
배운 점처음 카드팩 TC는 확인 항목을 한 줄에 묶어 55건뿐이었음 → 규칙에 "요소·문구·값마다 TC" 같은 커버리지 규칙을 넣자 338건으로 늘고 실제 결함을 찾음. 같은 규칙으로 기존 두 게임을 다시 훑자 결함·불일치 5건이 더 나옴. AI 결과의 품질은 규칙을 얼마나 구체적으로 주느냐에 달려 있었습니다. 또 처음 실패한 테스트 중 상당수는 테스트 쪽 문제(예: 페이지를 열자마자 눌러 쿨다운에 걸림)여서, 실패를 바로 결함으로 보지 않고 원인을 나눠 보는 과정이 필요했습니다.

한계와 다음 단계

  • TC 작성 단계는 제 PC의 Claude Code에서 돌립니다. 나머지(점검·테스트·리포트·Jira)는 AI 없이 돌아갑니다.
  • 자동 테스트는 웹(html) 게임 대상입니다. 유니티 게임은 Unity Test Framework(무료)로 같은 리포트·Jira 흐름에 붙이는 것을 다음 단계로 보고 있습니다.
  • 기획서 대비 빠진 항목 찾기는 글자 비교라서 후보일 뿐이고 사람이 확인해야 합니다.
  • GitHub Actions로 올릴 때마다 테스트를 자동 실행하는 것도 다음 단계입니다.
