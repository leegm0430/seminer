무엇을 만들었나

자료를 첨부하면 TC 작성 → 규칙 점검 → 게임 자동 테스트 → 결과 리포트·TC 엑셀 → Jira 이슈 등록까지 이어지는 흐름입니다. 자료는 기획서(PDF·MD·TXT), 화면 이미지, 기존 TC 엑셀, 게임 파일 무엇이든 넣을 수 있고, 넣은 자료에 따라 진행이 달라집니다. 중심에는 제가 정리한 TC 작성 규칙이 있고, AI가 TC를 쓸 때와 점검 도구가 TC를 볼 때 모두 이 규칙을 따릅니다.

자료 첨부→ TC 작성 (Claude Code + TC 작성 규칙)→ 규칙 점검→ Playwright 자동 테스트→ 리포트·TC 엑셀→ Jira TC·버그 이슈

첨부한 자료에 따라 이렇게 진행됩니다

첨부한 자료진행 순서
기획서
PDF·MD·TXT
  1. 자료 정리: PDF에서 글자를 뽑고, 글자가 거의 없는 그림·플로우 차트 쪽은 이미지로 만들어 따로 읽음
  2. 기획서를 장·쪽 단위 근거로 나눠 근거 대응표를 만들고, 근거마다 규칙대로 TC 작성 (근거에 TC 0건인 칸이 없게)
  3. 기획서 안에서 서로 다른 부분·빠진 부분을 "기획서 확인 필요"로 정리
이미지
화면 캡처·UI 시안
  1. 화면마다 버튼·입력칸·표시 정보·안내 문구 목록을 만듦
  2. 요소마다 보이는지(노출) TC와 눌렀을 때(동작) TC를 짝으로 작성, 비활성 상태가 있으면 활성·비활성 짝
기존 TC 엑셀
XLSX
  1. 시트를 읽어 TC 시트를 찾고 규칙으로 점검 (빈 칸, 묶인 기대 결과, 번호 중복 등)
  2. 고칠 점을 목록으로 제안 — 원본 엑셀은 고치지 않음
  3. 게임이 있으면 자동화할 TC를 골라 테스트 코드를 작성
  4. 규칙으로 빠진 TC를 찾아 별도 번호·시트로 보충
게임 파일
웹 html
  1. TC마다 Playwright 테스트 코드를 작성하고 크롬에서 실행
  2. 결과를 HTML 리포트와 TC 엑셀(PASS / Fail / N/T)에 기록
  3. 실패는 원인을 나눠(테스트 코드 / 게임 결함 / 기획과 다름) 결함만 Jira 버그로 등록
게임 파일 없음자동 테스트를 건너뛰고 검토 리포트(기존 TC 고칠 점 · 기획서 확인 필요 · 추가 제안)로 마무리

TC 작성 규칙 (공개 자료 + 제가 쓴 TC 2종을 참고해 정리)

  • 한 줄 쓰기 — TC 하나에 확인 하나, 기대 결과는 눈으로 확인할 수 있는 결과(숫자·화면 문구 그대로)
  • 무엇을 TC로 — 정상·실패 짝, 경계값(n−1·n·n+1), 끊김·환경, 확률은 시행 횟수와 판정 범위
  • 빠짐없이(커버리지) — 화면 요소·안내 문구·규칙 값마다 TC, 근거(기획서 조항·화면)마다 TC가 0건인 칸이 없게

AI가 쓴 TC는 모두 초안이며 제가 검토 중입니다(엑셀의 검토 칸). Jira에는 기존 TC·결함을 등록했고, 이번에 보충한 TC는 아직 올리지 않았습니다.

어떻게 테스트했나

  • 내부 값을 읽을 수 있는 게임(BLOODFALL·카드팩): 게임 상태를 직접 맞춰 원하는 상황을 빠르게 만들고(보스 등장 직전, 체력 30% 등) 화면과 값을 함께 판정
  • 내부 값이 숨겨진 게임(슬라임): 페이지가 열리기 전에 물리 엔진 생성 함수를 감싸, 원하는 단계 슬라임을 원하는 자리에 놓아 병합 점수·경고선 경계(59/60/61%)를 확인
  • 온라인 기능: 실제 P2P 대신 가짜 연결로 연결 문구·시간 초과(시계를 빠르게 돌림)·승패 메시지를 확인, 실제 두 기기 연결은 수동 TC로 남김
  • 무작위: 난수를 고정하거나, 확률은 수천~수만 번 뽑아 범위로 판정 (예: 아이템 박스 2,000마리 중 70~130개)

버그·문제가 생기면 Jira에 이렇게 저장됩니다

자동 테스트가 끝나면 결과 파일을 읽어 Jira 무료 플랜(REST API)에 올립니다. 토큰은 제 PC의 설정 파일에만 두고, 설정이 없으면 Jira에 보내지 않고 보낼 내용만 파일로 저장하는 드라이런으로 돕니다.

  1. TC를 먼저 이슈로 — TC마다 작업 이슈 [TC 번호] 제목을 만듭니다. 본문에 게임·원본 TC·기획서 근거·자동화 여부·검토 상태, 라벨에 TC · 게임 이름 · 자동/수동. 한 번 올린 TC는 다시 올리지 않습니다.
  2. 실패한 테스트를 찾기 — 테스트 결과에서 실패·시간 초과만 고릅니다. 테스트 이름에 TC 번호가 들어 있어 어느 TC가 실패했는지 바로 압니다.
  3. 버그 이슈 만들기 — 제가 쓰던 버그 리포트 템플릿과 같은 양식으로 본문을 채웁니다. 제목은 [자동] [모듈] 무엇이 — "기대 결과" 아님, 라벨은 auto-qa · 게임 이름 · 초안.
    • 항목 표 — 발견일, 보고자, 모듈/기능(TC 분류), 우선순위(TC 우선순위로 제안), 심각도(재현 후 지정), 재현율, 상태
    • 발생 환경 — 게임 파일과 수정일, 크롬·화면 1280×800, OS, 실행 시각
    • 사전 조건 · 재현 스텝 · 기대 결과 — 실패한 TC 내용을 그대로 옮김
    • 실제 결과 — 오류 원문 (기대 값과 실제 값 — 예: 결과 창 19,472점, 3초 뒤 보드 19,984점)
    • 비고 — 진행 전 체크리스트(직접 재현되는가, 기대 결과의 근거가 있는가, 심각도·우선순위 구분)
  4. 증거 붙이기 — 실패 순간 스크린샷을 첨부하고, 관련 TC 이슈와 "관련 있음(Relates)"으로 연결합니다.
  5. 같은 실패는 새 이슈 대신 댓글 — 이미 올린 실패가 다시 나오면 "○월 ○일 실행에서 다시 실패 (누적 n회)" 댓글과 오류 내용을 기존 이슈에 답니다. 이슈 번호는 PC의 기록 파일에 남겨 중복 등록을 막습니다.
  6. 사람이 마무리 — 자동으로 만든 버그는 모두 초안입니다. 제가 직접 재현한 뒤 진행하고, 재현되지 않으면 테스트 쪽 문제로 분류합니다.

역할 · 배운 점 · 검증 · 한계

역할

TC 작성 규칙과 테스트 대상·범위, AI 결과의 검토·채택은 제가 정하고, TC 초안·테스트 코드·도구 코드는 Claude Code가 작성했습니다.

배운 점

카드팩 TC는 처음 확인을 한 줄에 묶어 55건뿐이었지만, 규칙에 "요소·문구·값마다 TC"를 넣자 338건이 되고 실제 결함을 찾았습니다. 같은 규칙으로 다른 두 게임을 다시 보자 결함·불일치 5건이 더 나왔습니다. AI 결과의 품질은 규칙을 얼마나 구체적으로 주느냐에 달려 있었습니다.

검증

처음 실패한 테스트 13개 중 11개는 테스트 쪽 문제(예: 페이지를 열자마자 눌러 드롭 쿨다운에 걸림)였습니다. 실패를 바로 결함으로 보지 않고 원인을 나눈 뒤에 결함으로 기록했습니다.

한계·다음

TC 작성은 제 PC의 Claude Code가 필요하고, 자동 테스트는 웹 게임 대상입니다. 온라인 기능은 가짜 연결로 화면 처리만 확인합니다. 다음 단계는 유니티 게임(Unity Test Framework)과 GitHub Actions 자동 실행입니다.
